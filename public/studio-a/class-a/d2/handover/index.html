先懂這件事，後面 20 步才有意義

這套系統的五個鎖，全長在兩個「總後台帳號」上 —— 一個 Cloudflare 帳號（網站、資料庫、門禁都掛在它底下）、 一個 GitHub 帳號（程式碼保管庫的擁有者）。 所以交接不是搬檔案，是這兩個帳號的主權移交 ＋ 換一把共用鑰匙。

全篇最重要的一條順序

先移名單、再換鎖。

這套系統的鑰匙 ——「讓程式讀寫資料庫」的那把 —— 就寫在程式碼裡。當初是刻意這樣設計的：13 個人各自把程式碼複製一份到自己電腦，就能直接開工，不必一個一個發鑰匙。

代價是：只要還在協作者名單上，就抓得到最新的程式碼，連同裡面最新的那把鑰匙。

所以順序反了會這樣 —— 你先撤銷了舊鑰匙、發了新的、寫進程式碼上傳，但名單還沒清。名單上的人在自己電腦按一次更新，新鑰匙就到手了。等於白換。

先把該移的人移出名單，他就抓不到新的程式碼了；這時候再換鑰匙，舊的那把才真的作廢。

§2 帳號主權移交 0 / 3
誰做：接手人親自操作，講師在旁邊看　·　什麼時候：交接當天
這一段的順序不能換

先換信箱，再換那兩個帳號。

aidata@ 這個信箱是最上游的一把鎖 —— GitHub 和 Cloudflare 都用它註冊，密碼忘了就從那裡寄重設連結進來。 誰收得到那個信箱的信，誰就能把那兩個帳號的密碼重設掉。

所以只改那兩個帳號、不換信箱密碼的話，講師照樣能從信箱把它們設回來 —— 等於沒交接。信箱先換，後面兩個才算數。

另外，每個帳號內部也有順序：先改密碼，再撤銷舊授權。改密碼不會讓已經發出去的指令列授權失效，撤銷授權那一步才是真的把講師電腦踢掉。

動手前先開一個記事本。 這一段會當場改掉三組密碼（信箱、GitHub、Cloudflare），新密碼只有你自己知道、講師不會知道 —— 沒記下來，離開這個會議就找不回來了。 記事本是今天的權宜；之後怎麼保管（密碼工具、紙本鎖起來）是公司自己的事，但不要用 email 或通訊軟體傳。

    登入後：設定 → 變更密碼（左側選單）。

    看一下畫面長什麼樣

    ① 左側選單的「變更密碼」　·　② 帳號欄會顯示 aidata@studioa.com.tw，確認是這個再往下填。

  2. 04

    GitHub 總後台帳號

    網址：github.com　·　帳號 aidata-studioa（用 aidata@studioa.com.tw 登入，密碼講師當場給）

    • 登入後，點右上角頭像 → 下拉選單選 Settings。
    • 左側選單 Password and authentication → 最上面那區 Change password。
      舊密碼填講師給的那組；新密碼你自己設，設完記進記事本。按 Update password。
    • 改完可能會問要不要登出其他裝置 —— 選要。沒問的話，去左側選單 Sessions，把不是你這台的全部 Revoke。
    • 左側選單 Applications → 上方分頁 Authorized OAuth Apps → 找到 GitHub CLI → 右邊按 Revoke。
    第 4 小步是這一格真正的重點。 改密碼不會讓已經發出去的授權失效 —— 講師電腦上的指令列工具是靠那筆授權在動的，撤銷它，那台電腦才真的進不來。

    GitHub 密碼要求至少 15 個字元，或 8 個字元含數字與小寫。

  3. 05

    Cloudflare 總後台帳號

    網址：dash.cloudflare.com　·　用 aidata@studioa.com.tw 登入（密碼講師當場給）

    前三步都在同一個地方：右上角頭像 → My Profile → 左側 Access Management。

    • 改密碼：dash.cloudflare.com/profile/access-management/authentication/password
      按 Change Password。
      舊密碼填講師給的那組；新密碼你自己設，設完記進記事本。
    • 登出其他裝置：dash.cloudflare.com/profile/access-management/sessions
      把不是你這台的全部登出（你自己那筆會標「Current Session」，留著）。
    • 撤銷指令列工具的授權：dash.cloudflare.com/profile/access-management/authorization
      找到 Wrangler → 右邊 Revoke。
    • 換掉付款方式：dash.cloudflare.com/…/billing/subscriptions。這一步要帶一張你自己的信用卡，細節見下方紅框。
    第 3 小步是這一格的重點，跟前一格的道理一樣。 那筆 Wrangler 授權是 2026-08-07 建站當天留下的，有 28 個權限（涵蓋網站、資料庫、儲存空間）， 而且改密碼不會讓它失效 —— 撤銷它，講師的指令列工具才真的碰不到這個帳號。

    同一頁還有一筆 Cloudflare Access（1 個權限）—— 那是門禁系統自己的，留著不要動。 右上角的 Revoke all 也不要按，會把它一起撤掉。
    付款方式（第 4 小步）：目前掛的是講師個人的信用卡，連帳單地址也是他家。
    當初建站時，Cloudflare 的門禁服務（Zero Trust）即使用免費方案也要求綁一張卡，所以先用了講師的。 今天要換成你自己的卡（不必是公司卡，Cloudflare 只是要求有一張有效的卡在檔）。

    順序不能反 —— 先加後刪：
    ① Payment method 區塊按 + Add，加入你的卡，設為 Primary
    ② 確認新卡是 Primary 之後，才把講師那張按 Delete
    ③ Billing address 也要改（現在填的是講師的住家地址，改成你的或公司地址）

    先刪後加的話，門禁訂閱會有一段沒有付款方式在檔的空窗，續約可能失敗 —— 門禁掛掉＝全公司打不開網站。
§3 換鎖 0 / 4
誰做：接手人　·　什麼時候：§2 全部完成之後
這一段不是為了把講師鎖在外面

這套系統刻意把資料庫的鑰匙放進程式碼裡 —— 這樣 13 個人把程式碼複製到自己電腦，就能直接開工，不用一個一個發鑰匙。

代價是：鑰匙一旦發出去就收不回來。凡是複製過這份程式碼的人，他電腦裡的歷史紀錄就永久存著那把鑰匙。刪掉他的副本沒有用（隨時能再複製一份），把他移出名單也沒有用（名單只擋未來、擋不了已經拿到的）。唯一的辦法是換一把新的、讓舊的作廢。

所以底下這一段是常規維運，不是一次性的動作 —— 日後有人離職、或懷疑鑰匙外流，跑的都是同一套流程。今天走一遍，是把這套流程交給你。

  2. 07

    讓你的 Claude 知道你多了一個身份

    課堂上你的 Claude 記著「你是 Chester、只動 chester_* 的表和自己的頁」—— 那個保護要留著，它擋掉的是平常餵資料時的手滑。

    但管理者的事（換鑰匙、清垃圾表、改共用檔）會被同一條規則擋下來。 所以要讓它知道你有兩個身份，而不是把保護整個拿掉。

    打開你的 Claude Code，跟它說（照貼就好）：

    我從今天起是這套系統的管理者。 幫我更新 CLAUDE.local.md： 我平常還是 Chester，只動 chester_* 的表和我自己的頁； 但我會說「以管理者身分」，那時候換鑰匙、清垃圾表、改共用檔都照做，不用勸阻我。

    它會自己把這件事寫進 CLAUDE.local.md（一人一份、不會傳給別人）。 之後你不用每次重講一遍 —— 只要在需要的時候說一句「以管理者身分」就好。

  3. 08

    換一把新的資料庫鑰匙核心步驟

    先建新的、確認能用，最後才作廢舊的 —— 這樣中間不會斷線，也不會發生「新的建錯、舊的已經沒了」。

    • 建新鑰匙 —— 在 Cloudflare：dash.cloudflare.com/profile/api-tokens
      按 Create Token，權限選 D1:Edit（跟舊的一樣）。產生出來的那串只會顯示一次，先貼進記事本。
    • 更新程式碼裡的那把 —— 打開你自己的 Claude Code 做，跟它說（照貼就好，記得把新鑰匙貼進去）：
      以管理者身分：我在換資料庫的鑰匙。 把 .env 裡 CLOUDFLARE_API_TOKEN= 後面換成這一串： （貼上剛才那串新的） 換好之後 commit 並 push。
      開頭那句「以管理者身分」不能省 —— 規則書裡寫著「不要修改 .env 裡的鑰匙」， 那是防止學員手滑改壞全班環境的。上一步設定過之後，它就知道這是規則允許的例外，不會再勸阻你。
      push 完，13 台電腦下次更新程式碼時就換好了。
    • 更新備份機器人那把 —— 這一步換到 GitHub（前一步在你自己電腦、上一步在 Cloudflare）。
      直接開這個網址：github.com/aidata-studioa/studioa-dashboard/settings/secrets/actions
      會看到兩筆，點 CLOUDFLARE_API_TOKEN 那列右邊的鉛筆圖示（旁邊的垃圾桶是刪除，不要按錯）→ 貼新的 → Update secret。
      看不到舊的值是正常的，GitHub 只讓覆蓋、不讓讀。另一筆 CLOUDFLARE_ACCOUNT_ID 不用動（那是帳號編號、不是鑰匙）。
    • 驗一下新的能用 —— 還是在 GitHub：github.com/aidata-studioa/studioa-dashboard/actions
      左側選 Daily D1 export → 右邊 Run workflow 手動跑一次。跑出綠勾才算數，紅叉表示新鑰匙有問題，先別做下一步。
    • 作廢舊的 —— 回到 Cloudflare（同第 1 步那個網址），把 studioa-d1-edit 那列右邊的「⋯」→ Delete。
      做到這一步，舊鑰匙才真的死掉。
    第 3 小步最容易漏。 那是每晚自動備份用的鑰匙，跟程式碼裡那把是兩個地方、要各換一次。 只換程式碼、忘了這裡，隔天起備份天天失敗 —— 而且警報寄到那個沒人在讀的信箱，不會有人發現。 2026 年 8 月底備份斷了 8 天，就是這個劇本。

清掉最後 6 張封存表 —— 這件事系統故意不讓 AI 做

這套系統有一條規矩：刪除只是蓋章，不是真的刪。說一句「救回來」就回來了，所以誤刪不是災難。 代價是被蓋章的資料不會自己消失 —— 久了會堆成垃圾。

所以真刪除只有一條路：管理者自己登入 Cloudflare 後台，親手打指令。 程式擋著、Claude 也不代辦（指令列打 DROP TABLE 會被系統攔下來，這是刻意的）。 這不是麻煩 —— 能把資料真的抹掉的權力，只留給坐在這個位子上的人。今天起那個人是你。

直接開這個網址（會直接落在 studioa-db 的 Console 分頁）：
dash.cloudflare.com/…/d1/databases/…/console

從後台自己找的話：左側 Storage & databases → D1 SQLite Database → studioa-db → Console 分頁。

先跑這句看看現在還有幾張：

SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'zzold%' ORDER BY name;

應該回 6 列。確認數字對得上，就把下面這段整個貼進去執行（Console 吃得下多句）：

DROP TABLE zzold2_bob_actions; DROP TABLE zzold2_bob_categories; DROP TABLE zzold2_bob_items; DROP TABLE zzold2_bob_stores; DROP TABLE zzold2_bob_trend; DROP TABLE zzold2_bob_weekly;

跑完再執行一次上面那句 SELECT —— 這次應該一列都不回，代表清乾淨了。 然後把下面的清單勾起來。

為什麼這 6 張確定可以刪：它們是 2026-08-11（D2 開課前一天下午）講師彩排時建的練習表， 裡面是示範用的假資料（信義、天母、內湖那六家店），跟北一區示範頁的數字幾乎一樣。
⚠️ 表名裡的 bob 不是指同事的資料。 Bob 本人真正在用的表叫 bob_stores_weekly（504 列真實門市資料）， 不在這份清單裡、也不會被動到。名字前面有 zzold 的才是封存版。
