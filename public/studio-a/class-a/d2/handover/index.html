先懂這件事，後面 20 步才有意義

這套系統的五個鎖，全長在兩個「總後台帳號」上 —— 一個 Cloudflare 帳號（網站、資料庫、門禁都掛在它底下）、 一個 GitHub 帳號（程式碼保管庫的擁有者）。 所以交接不是搬檔案，是這兩個帳號的主權移交 ＋ 換一把共用鑰匙 ＋ 講師清場。

全篇最重要的一條順序

先移名單、再換鎖。

這套系統的鑰匙 ——「讓程式讀寫資料庫」的那把 —— 就寫在程式碼裡。當初是刻意這樣設計的：13 個人各自把程式碼複製一份到自己電腦，就能直接開工，不必一個一個發鑰匙。

代價是：只要還在協作者名單上，就抓得到最新的程式碼，連同裡面最新的那把鑰匙。

所以順序反了會這樣 —— 你先撤銷了舊鑰匙、發了新的、寫進程式碼上傳，但名單還沒清。名單上的人在自己電腦按一次更新，新鑰匙就到手了。等於白換。

先把該移的人移出名單，他就抓不到新的程式碼了；這時候再換鑰匙，舊的那把才真的作廢。

§2 帳號主權移交 0 / 3
誰做：接手人親自操作，講師在旁邊看　·　什麼時候：交接當天
這一段的順序不能換

先換信箱，再換那兩個帳號。

aidata@ 這個信箱是最上游的一把鎖 —— GitHub 和 Cloudflare 都用它註冊，密碼忘了就從那裡寄重設連結進來。 誰收得到那個信箱的信，誰就能把那兩個帳號的密碼重設掉。

所以只改那兩個帳號、不換信箱密碼的話，講師照樣能從信箱把它們設回來 —— 等於沒交接。信箱先換，後面兩個才算數。

另外，每個帳號內部也有順序：先改密碼，再撤銷舊授權。改密碼不會讓已經發出去的指令列授權失效，撤銷授權那一步才是真的把講師電腦踢掉。

動手前先開一個記事本。 這一段會當場改掉三組密碼（信箱、GitHub、Cloudflare），新密碼只有你自己知道、講師不會知道 —— 沒記下來，離開這個會議就找不回來了。 記事本是今天的權宜；之後怎麼保管（密碼工具、紙本鎖起來）是公司自己的事，但不要用 email 或通訊軟體傳。

    先換公司信箱的密碼這一步要第一個做

    信箱：aidata@studioa.com.tw　·　webmail：http://studioa.com.tw:8080
    登入後：設定 → 變更密碼（左側選單）。

    看一下畫面長什麼樣

    ① 左側選單的「變更密碼」　·　② 帳號欄會顯示 aidata@studioa.com.tw，確認是這個再往下填。
    三個欄位由上到下：舊密碼（講師當場給）、新密碼、確認新密碼，然後按左下角「儲存」。

  2. 04

    GitHub 總後台帳號

    網址：github.com　·　帳號 aidata-studioa（用 aidata@studioa.com.tw 登入，密碼講師當場給）

    • 登入後，點右上角頭像 → 下拉選單選 Settings。
    • 左側選單 Password and authentication → 最上面那區 Change password。
      舊密碼填講師給的那組；新密碼你自己設，設完記進記事本。按 Update password。
    • 改完可能會問要不要登出其他裝置 —— 選要。沒問的話，去左側選單 Sessions，把不是你這台的全部 Revoke。
    • 左側選單 Applications → 上方分頁 Authorized OAuth Apps → 找到 GitHub CLI → 右邊按 Revoke。
    第 4 小步是這一格真正的重點。 改密碼不會讓已經發出去的授權失效 —— 講師電腦上的指令列工具是靠那筆授權在動的，撤銷它，那台電腦才真的進不來。

    GitHub 密碼要求至少 15 個字元，或 8 個字元含數字與小寫。

  3. 05

    Cloudflare 總後台帳號

    網址：dash.cloudflare.com　·　用 aidata@studioa.com.tw 登入（密碼講師當場給）

    前三步都在同一個地方：右上角頭像 → My Profile → 左側 Access Management。

    • 改密碼：Access Management → Authentication → 上方分頁 Password → Change Password。
      舊密碼填講師給的那組；新密碼你自己設，設完記進記事本。
    • 登出其他裝置：Access Management → Active sessions。
      把不是你這台的全部登出（你自己那筆會標「Current Session」，留著）。
    • 撤銷指令列工具的授權：Access Management → Connected Applications → 找到 Wrangler → 右邊 Revoke。
    • 換掉付款方式：回帳號首頁 → 左側最下面 Manage account → Billing。這一步要帶一張你自己的信用卡，細節見下方紅框。
    第 3 小步是這一格的重點，跟前一格的道理一樣。 那筆 Wrangler 授權是 2026-08-07 建站當天留下的，有 28 個權限（涵蓋網站、資料庫、儲存空間）， 而且改密碼不會讓它失效 —— 撤銷它，講師的指令列工具才真的碰不到這個帳號。

    同一頁還有一筆 Cloudflare Access（1 個權限）—— 那是門禁系統自己的，留著不要動。 右上角的 Revoke all 也不要按，會把它一起撤掉。
    付款方式（第 4 小步）：目前掛的是講師個人的信用卡，連帳單地址也是他家。
    當初建站時，Cloudflare 的門禁服務（Zero Trust）即使用免費方案也要求綁一張卡，所以先用了講師的。 今天要換成你自己的卡（不必是公司卡，Cloudflare 只是要求有一張有效的卡在檔）。

    順序不能反 —— 先加後刪：
    ① Payment method 區塊按 + Add，加入你的卡，設為 Primary
    ② 確認新卡是 Primary 之後，才把講師那張按 Delete
    ③ Billing address 也要改（現在填的是講師的住家地址，改成你的或公司地址）

    先刪後加的話，門禁訂閱會有一段沒有付款方式在檔的空窗，續約可能失敗 —— 門禁掛掉＝全公司打不開網站。
§3 換鎖 0 / 5
誰做：接手人　·　什麼時候：§2 全部完成之後
這一段不是為了把講師鎖在外面

這套系統刻意把資料庫的鑰匙放進程式碼裡 —— 這樣 13 個人把程式碼複製到自己電腦，就能直接開工，不用一個一個發鑰匙。

代價是：鑰匙一旦發出去就收不回來。凡是複製過這份程式碼的人，他電腦裡的歷史紀錄就永久存著那把鑰匙。刪掉他的副本沒有用（隨時能再複製一份），把他移出名單也沒有用（名單只擋未來、擋不了已經拿到的）。唯一的辦法是換一把新的、讓舊的作廢。

所以底下這一段是常規維運，不是一次性的動作 —— 日後有人離職、或懷疑鑰匙外流，跑的都是同一套流程。今天走一遍，是把這套流程交給你。

  2. 07

    換一把新的資料庫鑰匙核心步驟

    先建新的、確認能用，最後才作廢舊的 —— 這樣中間不會斷線，也不會發生「新的建錯、舊的已經沒了」。

    • 建新鑰匙：Cloudflare 右上角頭像 → My Profile → API Tokens → Create Token，權限選 D1:Edit（跟舊的一樣）。產生出來的那串只會顯示一次，先貼進記事本。
    • 更新程式碼裡的那把 —— 打開你自己的 Claude Code 做，跟它說（照貼就好，記得把新鑰匙貼進去）：
      我是這套系統的管理者，現在在換資料庫的鑰匙。 把 .env 裡 CLOUDFLARE_API_TOKEN= 後面換成這一串： （貼上剛才那串新的） 換好之後 commit 並 push。
      第一句不能省。 系統的規則書裡寫著「不要修改 .env 裡的鑰匙」—— 那是防止學員手滑改壞全班環境的，管理者換鑰匙是例外，講清楚身分它才會動手。
      push 完，13 台電腦下次更新程式碼時就換好了。
    • 更新備份機器人那把：repo → Settings → Secrets and variables → Actions → CLOUDFLARE_API_TOKEN → 鉛筆圖示 → 貼新的 → Update secret。
    • 驗一下新的能用：repo → Actions → Daily D1 export → Run workflow 手動跑一次，綠燈才算數。
    • 作廢舊的：回 Cloudflare API Tokens，把 studioa-d1-edit 撤銷。做到這一步，舊鑰匙才真的死掉。
    第 3 小步最容易漏。 那是每晚自動備份用的鑰匙，跟程式碼裡那把是兩個地方、要各換一次。 只換程式碼、忘了這裡，隔天起備份天天失敗 —— 而且警報寄到那個沒人在讀的信箱，不會有人發現。 2026 年 8 月底備份斷了 8 天，就是這個劇本。
  3. 08

    發一則訊息給大家

    鑰匙換掉之後，13 個人電腦裡的舊鑰匙就失效了。他們要更新一次程式碼才會拿到新的 —— 但正常開工流程本來就會做這件事，所以多數人不會察覺。

    發一則訊息讓大家心裡有底就好（可以直接複製）：

    dashboard 的資料庫鑰匙今天換過了。 下次開工的時候，先跟 Claude 說一句「先更新一下程式碼」再開始， 就會自動拿到新的鑰匙，不用做別的事。 如果餵數字的時候跳出認證錯誤（401），就是這個原因， 更新完就好了。
    挑非回報日做。 從舊鑰匙作廢、到每個人更新拿到新的之間，餵數字會失敗。
  4. 09

    讓你的 Claude 知道你多了一個身份

    課堂上你的 Claude 記著「你是 Chester、只動 chester_* 的表和自己的頁」—— 那個保護要留著，它擋掉的是平常餵資料時的手滑。

    但管理者的事（換鑰匙、清垃圾表、改共用檔）會被同一條規則擋下來。 所以要讓它知道你有兩個身份，而不是把保護整個拿掉。

    打開你的 Claude Code，跟它說（照貼就好）：

    我從今天起是這套系統的管理者。 幫我更新 CLAUDE.local.md： 我平常還是 Chester，只動 chester_* 的表和我自己的頁； 但我會說「以管理者身分」，那時候換鑰匙、清垃圾表、改共用檔都照做，不用勸阻我。

    它會自己把這件事寫進 CLAUDE.local.md（一人一份、不會傳給別人）。 之後你不用每次重講一遍 —— 只要在需要的時候說一句「以管理者身分」就好。

  5. 10

    講師清場 —— 當場做給接手人看

    • 刪掉電腦上兩份程式碼副本。
    • 登出部署工具（wrangler logout）。
    • 登出 GitHub 指令列的兩個帳號（gh auth logout）。

    這三件做完，講師這台電腦就跟這套系統沒有關係了 —— 但真正讓它進不來的是上面第 08 步（舊鑰匙作廢）和 §2 的撤銷授權，不是刪檔案。刪檔案是眼見為憑，作廢鑰匙才是實質。

所以真刪除只有一條路：管理者自己登入 Cloudflare 後台，親手打指令。 程式擋著、Claude 也不代辦（指令列打 DROP TABLE 會被系統攔下來，這是刻意的）。 這不是麻煩 —— 能把資料真的抹掉的權力，只留給坐在這個位子上的人。今天起那個人是你。

第三段 · 今天之後

接下來這七件事是你的了

上面是一次性的動作，做完就過去了。這一段是常設的 —— 系統平常怎麼顧、什麼時候該找人。

① 警報要有人固定讀

備份失敗、部署失敗、用量超標，所有警報都寄到 aidata@ 那個信箱。

2026 年 8 月底，每晚備份連續斷了 8 天沒人知道 —— 不是系統沒發警報，是警報沒有收件人。 指定一個人每週看一次就夠，這是整份手冊裡最便宜、也最容易被跳過的一件事。

② 每天早上的備份要是綠燈

GitHub → repo → Actions 分頁 → 「Daily D1 export」。正常是一整排綠勾，每天一個備份檔進 exports/。

出現紅叉且連兩天沒好，就是要處理的訊號。

③ 誰的表變大，就要加索引

某個人的資料表長到上萬列之後，整站會開始變慢 —— 不只他自己的頁，連首頁卡片牆都會被拖住。

處理方式寫在 repo 的 CLAUDE.md 第 9 節：加一個「時間欄索引」再跑一次 ANALYZE。 兩件都要做 —— 只加索引不跑 ANALYZE，系統會繼續用舊的走法，等於沒加。

④ 價量頁那行小字

財會的價量頁，累計區塊旁邊有一行「累計資料建於 ⋯」。

它的意思是：時間沒動 ＝ 累計還沒跟上最新的數字。正常匯資料會自己更新；如果是手改了某一筆，就可能對不上。看到時間停在很久以前，跟資料負責人說一聲重算就好。

⑤ 每月 5 美元，建議升級

資料庫目前用免費方案，每天的讀取量有上限。2026 年 9 月已經逼近上限兩次， 第二次全公司當天讀不到報表。

系統這邊已經做過優化（讀取量降到十分之一左右），但資料只會越來越多。 升級到 Workers Paid（約 US$5／月）等於把這個上限拿掉，在 Cloudflare 後台 Billing 頁掛公司卡就好。 這是治本，上面的優化只是把時間買回來。

⑥ 什麼時候該回頭找講師

報表頁明顯變慢，而且不是單一個人的問題 —— 通常代表有人的資料量級跳了一階（例如從月報改成日報、從分類明細改成單品明細）。

想要現在做不到的東西：例如累計目前一律是「當年 1 月到這個月」， 不支援「往回推 12 個月」那種滾動式的算法。要改是可以，但那是重做一段，不是改個設定。

一年後還有一件小事：備份每天都進保管庫，一年大約長 1 GB。2027 年第一季前不用理它。

⑦ 兩個帳號要不要再加一道鎖

目前兩個總後台帳號都只有密碼這一道鎖。這不是設定錯誤，是還沒決定要不要加 —— 加不加是公司的政策，今天的流程用不到。

如果之後決定要加第二道（登入時多驗一次身分）：GitHub 可以用手機內建的 Face ID／指紋，或簡訊，都不必另外裝 App；Cloudflare 只支援驗證器 App 或實體金鑰，沒有簡訊這個選項。兩邊都是進各自的帳號設定頁自己開，五分鐘的事。

另外，交接當天記在記事本上的那三組密碼，記得搬進公司的密碼管理工具或鎖進保險箱，然後把記事本刪掉。三條不要破：不要用 email 或通訊軟體傳、每個帳號不要用同一組、備援知情人要拿得到。

公司信箱那組值得再看一眼：那套 webmail 只要求六個字元、也不檢查強度，但它是另外兩個帳號的救援路徑 —— 系統沒擋，不代表可以設短的。有空的話回頭把它換長一點。
