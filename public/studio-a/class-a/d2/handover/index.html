先懂這件事，後面 20 步才有意義

這套系統的五個鎖，全長在兩個「總後台帳號」上 —— 一個 Cloudflare 帳號（網站、資料庫、門禁都掛在它底下）、 一個 GitHub 帳號（程式碼保管庫的擁有者）。 所以交接不是搬檔案，是這兩個帳號的主權移交 ＋ 換一把共用鑰匙 ＋ 講師清場。

全篇最重要的一條順序

先移名單、再換鎖。 名單擋新的、換鎖才作廢舊的。順序反了，還在名單上的人只要更新一次程式碼，就拿到新鑰匙。

§0 交接前決定 0 / 3
誰做：貴公司　·　什麼時候：交接日之前先決定好，當天才不會卡住
現況（2026-08-13 查核）

兩個總後台帳號目前都沒有開二階段驗證 —— 也就是說，密碼是唯一的一道鎖。
這不是錯誤設定，是還沒決定。下面第 02 步要決定的是「要不要開」，不是「怎麼重綁」；打開設定頁不會看到既有的驗證裝置要換掉。

  1. 01

    指定接手管理者一人

    就是「拿到兩組密碼的那個人」。建議另外指定一位備援知情人 —— 只有一個人知道密碼，那個人休假或離職時系統就沒人進得去。

  2. 02

    決定要不要開二階段驗證兩個帳號目前都沒開

    常見誤解是「一定要裝一個驗證器 App」——不是。兩個平台能選的方式不一樣：

    • GitHub：可選手機內建的 passkey（Face ID／指紋）或簡訊，都不用另外裝 App。
    • Cloudflare：只支援驗證器 App／實體金鑰，沒有簡訊選項。

    不開也是一個合理選擇 —— 救援信箱本來就在公司手上。但那樣密碼就是唯一一道鎖，第 03 步的保管方式要更嚴，而且兩個帳號的密碼不要用同一組。

    決定了就往下走：開 → 第 09、10 步各多一個設定動作；不開 → 那兩步就只有改密碼跟撤授權。

  3. 03

    決定密碼保管方式

    公司的密碼管理工具，或紙本鎖進保險箱。不要用 email 傳密碼。

    第 02 步若決定不開二階段驗證，這一步就是整套系統的最後一道防線 —— 兩組密碼各自獨立、只有指定的兩個人知道。

§1 清場 0 / 5
誰做：講師　·　什麼時候：D3 之前就能做完
  1. 04

    補齊協作者缺口

    有四位學員不在協作者名單上、也沒有待接受的邀請（名單見交接當天點交的紙本）。確認他們報名頁有沒有填 GitHub 帳號，補發邀請 —— D3 當天要動手，名單得先齊。

  2. 05

    刪掉 13 張封存表

    彩排殘留：zzold_bob_* ×6、zzold2_bob_* ×6、zzold_ztest_weekly ×1。要到 Cloudflare 的 D1 主控台手動刪。

    指令列刪不掉是刻意設計的 —— 這正是課堂教的那條界線：清垃圾由管理者到後台親手做，不交給 AI 代辦。

  3. 06

    檢查 submissions 表

    過一眼，確認沒有測試殘留的資料。

  4. 07

    留一份最新備份

    exports/ 底下存一份最新的，然後上傳（push）。

  5. 08

    移除課前測試帳號已完成 8/12

    課堂用的學員視角測試帳號已於 D2 完課日移除。D3 主題換成 skill／知識管理／投影片，不再需要它。

§2 帳號主權移交 0 / 3
誰做：接手人親自操作，講師在旁邊看　·　什麼時候：交接當天
每個帳號內的順序不能省

改密碼 →（要開的話）設定二階段驗證 → 撤銷舊授權。
改密碼不會讓已經發出去的指令列授權失效 —— 撤銷授權那一步才是真的把講師電腦踢掉。兩個帳號誰先誰後都行，但帳號內的順序要照走。

  1. 09

    GitHub 總後台帳號

    • 改密碼 —— 接手人自己設，講師不知道新密碼。
    • §0 決定要開二階段驗證的話：在接手人的裝置上設定（passkey 或簡訊），下載救援碼（recovery codes）歸檔。決定不開就跳過這步。
    • Settings → Sessions：全部登出。
    • Settings → Applications → Authorized OAuth Apps：撤銷「GitHub CLI」等講師機器的授權。講師電腦裡的鑰匙到這一步才真的死掉。
  2. 10

    Cloudflare 總後台帳號

    • 改密碼。§0 決定要開二階段驗證的話一併設定（只能用驗證器 App／實體金鑰，沒有簡訊）。
    • Members 頁確認沒有多餘成員。
    • Billing 確認：免費方案、沒有掛任何講師的信用卡。
  3. 11

    跟 IT 確認救援信箱的收信權在公司手上

    兩個帳號都用公司信箱註冊，那個信箱是唯一的救援路徑 —— 密碼忘了要重設，就是從那裡寄連結進來。信箱本來就是公司申請的，這步只是確認一次收信權真的在公司手上。

    反過來說也成立：誰收得到那個信箱的信，誰就能重設這兩個帳號的密碼。信箱的權限範圍要跟第 01 步指定的兩個人對得上。

§3 換鎖 0 / 4
誰做：接手人　·　什麼時候：§2 全部完成之後
  1. 12

    GitHub 協作者名單過一遍

    13 位學員該在的在（§1 補齊之後）。講師的個人帳號若還在名單上，移除。

    github.com/…/settings/access
  2. 13

    門禁名單過一遍

    16 個 email 逐一核對。管理者自己的帳號要留著（不然自己也進不去網站）；其餘依公司決定。加或刪一行，當場生效。

    dash.cloudflare.com/…/access-controls/policies
  3. 14

    重發資料庫鑰匙核心步驟

    Cloudflare → API Tokens → 撤銷 studioa-d1-edit → 建一把新的（權限一樣 D1:Edit）→ 更新程式碼保管庫裡的 .env → 上傳（push）。13 台電腦下次更新就換好。

    挑非回報日做。 從撤銷舊鑰匙、到學員各自更新拿到新的 .env 之間，餵數字會失敗。多數情況學員開工時會自動更新、自己就好了；群組提醒一句「下次開工先讓它更新一下」更穩。
  4. 15

    講師清場 —— 當場做給接手人看

    • 刪掉電腦上兩份程式碼副本。
    • 登出部署工具（wrangler logout）。
    • 登出 GitHub 指令列的兩個帳號（gh auth logout）。
§4 驗收 —— 五招 0 / 5
誰做：接手人自己跑一遍　·　目的：確認鎖真的換好了，不是「聽說換好了」
  1. 16

    無痕視窗開網站 → 被攔下來要 email

    沒被攔＝門禁沒生效。

  2. 17

    不登入直接打資料網址（/api/…）→ 一個數字都不吐

    吐得出數字＝資料是裸的，繞過網頁就拿得到。

  3. 18

    接手人的電腦用新鑰匙連資料庫 → 通

    wrangler d1 execute studioa-db --remote --command "SELECT 1"

  4. 19

    舊鑰匙 → 被拒；講師電腦更新程式碼 → 被拒

    這一招是 D2 那句「我退出的時候，帶不走任何東西」的兌現。兩邊都要拒才算數。

  5. 20

    手冊三份點交

    程式碼保管庫的 README.md ＋ CLAUDE.md ＋ D2 投影片的「異動操作」那一頁（含上面兩條直達網址）。

    之後人員異動就照那一套：發三樣、收兩樣、換一把。
